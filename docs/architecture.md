# 아키텍처 제안 — v0.1

## 설계 상태

공통 플랫폼의 논리 설계이며 첫 구현 결정은 ADR-001을 따릅니다. 기본 방향은 모듈형 단일 애플리케이션과 관계형 데이터베이스이며, 독립 워커가 비동기 작업을 수행합니다. 프레임워크·DB 제품은 [ADR-001](adr/001-application-stack.md)에서 Django·PostgreSQL로 결정했습니다. 호스팅은 미확정입니다.

## 구성과 책임

| 구성 | 책임 |
|---|---|
| 직원 포털·운영 콘솔 | 역할별 화면, 카탈로그·티켓·자산·관리 기능 |
| API·인증 경계 | 세션 검증, 조직 범위, 입력 검증, 요청 추적 |
| 공통 플랫폼 | 권한, 설정 버전, 워크플로, 규칙, 감사, 파일 메타데이터 |
| 업무 모듈 | 서비스·자산·구성·구매·계약·소프트웨어의 불변 조건 |
| 관계형 DB | 트랜잭션, 관계·고유성, 이력, outbox·작업 상태 |
| 워커 | SLA 평가·알림·수집·대사·보고서·재시도 |
| 객체 저장소 | 비공개 첨부·추출 파일, 제한 시간 다운로드 |
| 외부 어댑터 | SSO·인사·메일·수집·모니터링·ERP 연결 |

## 모듈 경계

다른 모듈 테이블을 임의 수정하지 않고 공개 서비스 계약을 호출합니다. 초기에는 같은 DB 트랜잭션을 사용할 수 있으나 책임 모듈이 검증합니다. 분석용 조회 모델은 원장과 구분합니다. 범용 EAV로 모든 필드를 저장하지 않고 핵심 속성은 정형화하며 확장 속성은 유형·스키마 버전으로 검증합니다.

## 일관성과 비동기 처리

- 상태 변경·이력·outbox 이벤트를 같은 트랜잭션으로 기록합니다.
- 워커는 최소 1회 전달을 전제로 이벤트 ID·대상 작업 고유키로 멱등 처리합니다.
- 재시도 횟수·지연·최종 실패 보관·관리자 재처리·외부 요청 추적을 제공합니다.
- 상태 변경 API는 현재 버전과 허용 전이를 검증합니다. 재고는 원자적 차감·예약으로 보호합니다.
- 외부 시스템 호출 성공과 로컬 커밋 사이의 실패에는 조회·대사·보상 절차를 둡니다.
- SLA 작업은 만료 후보 인덱스로 조회합니다. 이력으로 마감 산정 근거를 복원할 수 있어야 합니다.

## 보안 경계

기업 SSO는 OIDC/SAML 후보입니다. 관리자·연동 계정 권한을 분리하고, 조직·레코드 필터를 서버에서 강제합니다. 파일 링크 발급 전 매번 접근을 검증합니다. 인덱스·캐시 키에도 조직 범위를 포함합니다. 초기 조직 범위는 SaaS 고객사 격리의 보증이 아니며, SaaS 전환 전 tenant 경계·DB 정책·키·백업·침투 검증을 별도 설계합니다.

워크플로 조건은 제한된 표현식과 허용 동작으로 시작합니다. 임의 사용자 스크립트 실행은 초기 범위에 포함하지 않습니다. 설정 게시·권한 변경도 감사 대상입니다.

## 운영과 배포

개발·검증·운영 환경과 비밀정보를 분리합니다. 스키마 변경은 버전 관리하고 확장→데이터 이관→구버전 제거 방식으로 적용합니다. 복원 테스트로 데이터·파일의 일관성을 확인합니다. 구조화 로그·요청 ID·작업 지연·SLA 평가 지연·연동 실패율을 수집합니다. 검색은 초기 DB 기능에서 시작하고 규모 근거가 생기면 별도 엔진을 평가합니다.
