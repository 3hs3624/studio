# 엔티티 기본 필드와 데이터 관계

엔티티 목록에서 코드·이름을 등록한 후 상세 화면의 필드 그리드에서 업무 필드를 구성합니다.
빈 엔티티도 생성할 수 있으며 업무 필드는 최대 30개입니다. 시스템 필드 8개는 이 제한에 포함하지 않습니다.

## 자동 제공 시스템 필드

id(UUID), organization_id, created_at, created_by, updated_at, updated_by, row_version, schema_version_id.
서버에서 관리하며 업무 필드로 이름을 재사용하거나 데이터 입력으로 덮어쓸 수 없습니다.
생성자·수정자는 Person 식별자이며 비활성화된 계정도 기존 참조를 유지합니다.
현재 데이터는 추가 방식으로 보존합니다. 수정자·수정일은 등록 시 기록하며, 기존 레코드 수정·삭제 API는 이번 범위에 포함하지 않습니다.
상태·담당자·업무번호·논리 삭제는 공통 필드로 강제하지 않습니다. 해당 선택 기능의 실제 실행 기능은 별도 구현 범위입니다.

## 관계 유형

참조 필드에 대상 엔티티와 관계 유형을 지정합니다. 관계 방향은 현재 엔티티에서 참조 대상 기준입니다.

| 관계 | 입력값 | 제약 |
|---|---|---|
| 다대일 N:1 (기존 참조의 기본값) | 대상 UUID 하나 | 여러 원본이 같은 대상을 참조 가능 |
| 일대일 1:1 | 대상 UUID 하나 | 같은 엔티티·필드의 다른 원본에서 대상 재사용 불가 |
| 일대다 1:N | UUID 목록 | 원본은 여러 대상 연결 가능, 같은 필드의 다른 원본에 대상 중복 연결 불가 |
| 다대다 N:M | UUID 목록 | 여러 원본과 여러 대상 연결 가능 |

복수 관계는 최대 100개이며 동일 대상의 중복 입력은 거부합니다.
대상은 현재 조직의 지정된 엔티티에 속하는 실제 데이터여야 합니다.
게시된 대상 엔티티만 선택할 수 있습니다. 자기 참조나 순환 정의는 먼저 기본 정의를 게시한 후 참조 필드를 추가합니다.
관계는 공통 중간 테이블 EntityRecordLink에 저장되며, FK·유일성·조직 일치·정의 일치 제약을 적용합니다.
원본 JSON 값과 관계의 대상도 일치해야 합니다. 관계 행은 기존 업무 데이터와 같이 변경·삭제하지 않습니다.
참조 중인 데이터는 FK PROTECT 및 기존 추가 전용 정책에 따라 물리 삭제하지 않습니다.

## 업무 속성을 가진 중간 엔티티

예: 사용자 ↔ 서비스의 담당 관계에 역할·적용일이 필요하다면 SERVICE_MEMBER 같은 엔티티를 생성합니다.

1. 사용자 엔티티와 서비스 엔티티를 먼저 게시하고 데이터를 등록합니다.
2. 중간 엔티티에서 user, service를 각각 필수 다대일 참조로 구성합니다.
3. 역할·적용일 등 일반 업무 필드를 추가합니다.
4. '중간 엔티티 설정'에서 왼쪽 필드 user, 오른쪽 필드 service를 지정합니다.
5. 초안 저장 후 게시합니다.

이후 같은 사용자·서비스 연결 쌍은 중복 등록할 수 없습니다. 같은 종류의 엔티티 양쪽을 연결하는 중간 엔티티도 지원합니다.
중간 엔티티의 생성은 운영자가 수행하며, 임의 물리 테이블 생성 SQL은 실행하지 않습니다.

## 읽기와 버전 관리

최근 데이터의 '연결 보기'에서 정방향·역방향 연결을 확인할 수 있습니다.
API: GET /api/v1/admin/entities/{entity_id}/records/{record_id}/relations
응답은 record(공통 필드 포함), links(방향·필드·원본/대상 ID), junctions(중간 엔티티와 업무 속성)를 포함합니다.
한 번에 각 200건까지 반환합니다. 대량 관계를 위한 페이지 조회는 후속 범위입니다.
목록·데이터 API 및 구성 화면은 개발자·운영자·시스템 관리자 권한을 확인합니다.

게시 정의와 기존 데이터는 기존 버전을 유지합니다.
데이터가 있는 참조 키의 대상·관계 유형 및 중간 엔티티의 양쪽 필드는 바꿀 수 없습니다.
관계 변경은 새 필드를 사용해야 하며 삭제한 옛 키를 재사용하더라도 과거 데이터의 관계 의미를 검사합니다.
기존 0011 DB를 0012로 올릴 때 수정자=생성자, 수정일=생성일, 데이터 버전=1로 채우고 기존 참조를 다대일 관계로 이관합니다.
과거 게시 정의의 내용·해시와 업무 값은 바꾸지 않습니다.

## 로컬 Docker 업데이트

기존 Studio 폴더, .env.ap/.env.db, access 및 Docker 볼륨을 삭제하거나 configure를 다시 실행하지 마십시오.

1. 기존 Studio 폴더에서 `python deploy/local_split/control.py backup`으로 DB를 백업합니다.
2. `python deploy/local_split/control.py stop`으로 AP·DB를 중지합니다. 볼륨은 보존됩니다.
3. 새 소스 ZIP을 별도 폴더에 압축 해제합니다.
4. 새 소스 파일을 기존 Studio 폴더에 덮어씁니다. ZIP에는 기존 비밀 설정·계정 파일이 포함되지 않습니다. 기존 폴더를 통째로 삭제·교체하지 마십시오.
5. 기존 Studio 폴더에서 아래를 실행합니다.

```powershell
python deploy/local_split/control.py up
python deploy/local_split/control.py verify
```

up이 이미지를 재빌드하고 기존 DB에 마이그레이션을 적용합니다. 계정·비밀번호는 재설정하지 않습니다.
이번 소스는 검증 스크립트의 파일 읽기를 UTF-8로 명시하여 한글 Windows 경로의 CP949 오류도 수정합니다.
자동 검증: SQLite·PostgreSQL, 기존 DB 업그레이드, 로컬 AP/DB Docker 새 설치·영속성 검증.
기존 Render 환경은 동일 커밋으로 별도 배포하며, 로컬 PC는 위 업데이트를 수행해야 반영됩니다.
