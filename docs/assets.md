# 자산 등록·지급·반납·이력 관리

기준일: 2026-11-04. AST-01/02의 일부 구현입니다. 구매·재고 수량 연동은 [추가 명세](purchasing-inventory.md)에서 확장했습니다. 회계·물리 폐기 실행은 포함하지 않습니다.

## 제공 업무

- /assets: 현재 권한으로 조회할 수 있는 자산 목록·상태 필터·자산번호/이름 검색
- /assets/new: 자산 등록. 자산번호·이름·모델·제조사·일련번호·위치·공개 여부·등록 사유
- /assets/{id}: 기본 정보·허용된 지급/반납 이력, 자산 관리자의 정보 정정·입고 확인·지급·반납·이동·폐기 처리
- /my-assets: 본인의 현재 지급 자산과 과거 지급·반납 기록. 반납 후 다른 직원에게 재지급되어도 본인의 기록만 표시
- 처리 중인 서비스 요청: 자산 관리 권한이 있으면 보관 중인 자산을 신청자에게 지급하고 요청과 연결

등록번호는 생성 후 수정하지 않습니다. 제조사+일련번호는 조직 내에서 중복될 수 없으며 일련번호가 있으면 제조사가 필요합니다. 식별자는 앞뒤 공백을 제거하고 대소문자를 구분합니다. 제조사·일련번호 정정은 미확인/보관 상태에서만 가능합니다. 이름·모델·공개 여부 정정은 폐기 처리 전까지 사유를 남겨 수행합니다. 삭제 API는 없습니다.

## 역할과 개인정보

| 역할 | 접근 |
|---|---|
| ASSET_MANAGER(자산 관리자) | 조직 내 전체 자산·이력 조회, 등록·정정·상태 처리 |
| RESOURCE_READER(자산·구성 조회) | 조직 내 전체 자산·사용자·일련번호·이력 읽기 전용 |
| 일반 직원 | 공개된 기본 자산 정보 또는 현재 본인 지급 자산 조회 |
| 본인 지급 이력 | 본인의 지급/반납 시각·당시 자산번호·이름·접근 가능한 관련 요청만 |

SERVICE_MANAGER·AGENT·ORG_ADMIN 역할만으로 자산 변경 권한을 부여하지 않습니다. 조직 관리자가 역할 관리 화면에서 ASSET_MANAGER를 별도로 부여할 수 있습니다. ASSET_MANAGER 자체가 CI 전체 조회 권한을 부여하지는 않습니다.

공개 자산의 기본 정보는 자산번호·이름·모델·위치·상태입니다. 일반 직원에게 다른 사용자의 이름·일련번호·내부 사유·전체 지급 이력을 반환하지 않습니다. 현재 본인에게 지급된 자산은 공개 여부와 무관하게 상세 조회가 가능하며 본인 사용 정보·일련번호도 볼 수 있습니다. 반납한 비공개 자산의 현재 정보는 조회할 수 없지만 /my-assets에서 본인의 과거 기록은 유지됩니다.

## 상태와 전이

| 현재 상태 | 허용 동작 | 결과 |
|---|---|---|
| UNVERIFIED(미확인) | VERIFY 입고 확인, MOVE 위치 정정 | 확인 후 STOCK 또는 미확인 유지 |
| STOCK(보관 중) | ISSUE 지급, MOVE 이동, RETIRE 폐기 처리 | IN_USE 또는 보관/폐기 |
| IN_USE(사용 중) | RETURN 반납, MOVE 이동 | STOCK 또는 사용자 유지한 이동 |
| RETIRED(폐기 처리) | 조회만 | 최종 상태 |

새 등록은 STOCK으로 시작합니다. **기존 조회 전용 자산은 실제 보유 상태를 알 수 없으므로 UNVERIFIED로 이관**하며 가상의 지급/등록 이력을 만들지 않습니다. 자산 관리자가 실물을 확인하고 VERIFY를 수행해야 지급할 수 있습니다.

지급은 같은 조직의 활성 사용자에게만 가능합니다. 비활성 사용자에게 신규 지급할 수 없으나 퇴사자의 장비를 회수할 수 있도록 반납은 가능합니다. 이미 사용 중인 자산의 중복 지급을 거부하고 사용자 변경은 반납→새 지급으로 기록합니다. 지급 중인 자산은 폐기 처리할 수 없습니다. RETIRE는 시스템 상태 기록이며 실제 물리적 폐기나 외부 회계 처리를 수행하지 않습니다. 이 버전에서 폐기 상태 복구·별도 폐기 승인 절차는 없습니다.

각 동작과 정보 수정에는 사유가 필수입니다. MOVE는 위치만 바꾸며 사용자를 변경하지 않습니다. 보관 상태에 열린 지급 기록이 존재하는 등 상태·기록 불일치를 발견하면 지급·이동·폐기 처리를 거부합니다.

## 기록과 정합성

Asset에는 상태·현재 사용자·row_version을 저장합니다. AssetCustody에는 지급 사용자·처리자·원 요청·지급 위치/사유와 반납 정보를 보존합니다. 자산별 열린 Custody는 DB의 부분 고유 제약으로 최대 1개입니다. 상태가 IN_USE일 때만 현재 사용자가 있어야 한다는 제약도 적용합니다.

AssetHistory는 등록·정정·확인·지급·반납·이동·폐기의 변경 전후 값과 주체·시각·사유를 보존합니다. DB에서 이력 수정·삭제, 지급 당시 정보 변경, 완료된 반납 기록 변경을 차단합니다. 조직 간 참조도 DB에서 거부합니다. 상태와 Custody의 일치는 업무 명령에서 검증하며 임의 SQL 쓰기의 모든 교차 행 상태를 보장하는 범용 제약은 아닙니다.

명령은 기존 조직→사용자 잠금 후 자산·현재 지급 기록을 잠그고 버전을 검사합니다. 자산·지급/반납·이력·감사·outbox를 한 트랜잭션으로 처리합니다. 같은 멱등키 재시도는 기록을 중복 생성하지 않습니다. 다른 키의 동시 지급 또는 동시 반납/이동은 같은 버전에서 하나만 성공합니다.

## 서비스 요청 연결

서비스 요청이 IN_PROGRESS이고 수령자가 신청자와 일치할 때 연결 지급이 가능합니다. 자산 관리자와 해당 요청의 처리 범위 권한이 모두 필요합니다. ASSET_MANAGER만 있는 담당자는 비공개 요청 내용을 자동으로 조회할 수 없습니다.

연결 시 expected_version(자산)과 expected_request_version(요청)을 각각 검사합니다. 지급 기록·TicketResource 연결·자산 버전·요청 버전을 함께 반영합니다. 지급 자체가 요청을 자동 완료하지는 않습니다. 여러 장비를 처리한 뒤 담당자가 요청 완료를 별도로 기록할 수 있습니다.

반납은 별도 처리 중인 반납 요청에 연결할 수도 있습니다. 별도 요청을 지정하지 않으면 원 지급 요청을 이력에 참조하며 이미 종료된 원 요청의 상태·버전은 변경하지 않습니다. 원 요청 참조는 Custody에도 유지합니다. 요청 상세에는 당시 지급/반납의 자산번호·이름·시각만 표시하며 자산의 이후 사용자 정보를 표시하지 않습니다. 자산 상세 링크는 현재 조회 권한이 있을 때만 제공합니다.

## API

기존 세션·CSRF·Idempotency-Key와 limit/cursor 규약을 사용합니다.

| 메서드·경로 | 입력·응답 |
|---|---|
| GET /api/v1/assets | q(이름/자산번호),status,limit,cursor → 현재 조회 범위의 자산 |
| POST /api/v1/assets | asset_no,name,model,location,portal_visible,reason 필수; manufacturer,serial_number 선택 → 201, Location |
| GET /api/v1/assets/{id} | 기본 정보·역할/본인 여부에 따른 상세 |
| PUT /api/v1/assets/{id} | name,manufacturer,model,serial_number,portal_visible,reason,expected_version |
| POST /api/v1/assets/{id}/actions | action,reason,expected_version. ISSUE는 person_id·location, RETURN/MOVE/VERIFY는 location. ISSUE/RETURN에 service_request_id·expected_request_version 선택 |
| GET /api/v1/assets/{id}/history | 전체 이력 읽기 권한 또는 본인 지급/반납 기록 범위, 페이지 규약 |
| GET /api/v1/my/assets | 현재 본인에게 지급된 자산 |
| GET /api/v1/my/asset-history | 본인 지급/반납 기록, 내부 변경값·사유는 제외 |

기관·사용자·상태·등록번호를 수정 API에 직접 주입할 수 없습니다. action별로 허용하지 않는 필드도 거부합니다. 다른 조직·접근 불가 자산은 404, 변경 권한 없으면 403, 중복·버전 충돌·상태 불일치는 409입니다. API 자산 응답에 status/version을 추가했습니다. 제조사·일련번호·사용자는 허용된 상세 응답에만 포함됩니다.

## 실행·검증과 제한

새 데모 DB에는 manager(서비스+자산 관리자), assetadmin(자산 관리자+조회), agent(처리+조회), employee, orgadmin 계정을 제공합니다. 기존 설치는 마이그레이션 후 필요한 사용자에게 ASSET_MANAGER를 명시적으로 부여하고 기존 자산의 입고 상태를 확인하십시오. 데모 기본 비밀번호는 없으며 기존 안내처럼 직접 지정합니다.

기존 테이블과 역할 제약을 변경하므로 마이그레이션 전후에 조직/불변 트리거를 안전하게 재설치합니다. 새 자산 역할·지급 데이터가 있는 DB를 백업/복원 계획 없이 이전 스키마로 되돌리지 마십시오. 역방향 마이그레이션 검증은 disposable 테스트 DB에서만 수행합니다.

검증은 등록·중복 번호/일련번호·확인·지급·반납·재지급·이동·폐기·역할·개인정보·이관 불일치·원자적 실패 복구를 포함합니다. PostgreSQL에서는 실제 별도 연결의 동시 지급 및 반납/이동 경합을 검증합니다. Chromium에서는 요청 연계 지급, 사용자 확인·반납·재지급 이후의 개인정보 가림과 모바일 화면을 확인했습니다.

후속: 다중 창고·수량 재고·예약, 구매/계약·보증·비용, 자산 유형별 확장 속성, 직원 인수 확인·전자 서명, 폐기 승인·복구, 자동 수집·라이선스·CI 관계 고도화입니다.

## 창고 관리 장비 연동

구매 입고로 생성된 장비는 StockAsset으로 품목·창고·입고 원장과 연결됩니다. 지급·반납·폐기에는 ASSET_MANAGER와 STOCK_MANAGER가 모두 필요합니다. RETURN API는 stockroom_id를 요구하며 해당 창고 위치로 반납합니다. 창고에 보관된 장비의 이동은 재고 이동 API를 사용해야 합니다. 수량·보관 위치·자산 이력·재고 원장을 하나의 트랜잭션으로 반영합니다. 기존 단독 등록 자산은 기존 규칙을 유지합니다.
