# SLA·업무 달력·알림 — 구현 명세

기준일: 2026-11-04. ITSM-06/07의 일부 구현입니다. IBM과의 기능 동등성을 의미하지 않습니다.

## 제공 범위

서비스 관리자는 /work/sla에서 업무 달력과 우선순위별 정책을 게시합니다. 조직 관리자는 서비스 관리자 역할 없이 정책을 게시할 수 없습니다. 공개 API도 같은 권한을 적용합니다.

접수 시 해당 조직·우선순위의 가장 높은 버전 정책을 선택하고 정책·달력 값을 SLAInstance.snapshot에 보존합니다. 해당 정책이 없으면 SLA 미적용으로 접수합니다. 정책이 나중에 게시되어도 기존 티켓에는 소급 적용하지 않습니다. 정책·달력의 수정/삭제 대신 새 레코드를 게시합니다. 기존 시계의 버전은 바뀌지 않습니다.

## 시간 계산

- 한 달력은 IANA 시간대, 업무 요일(월=0~일=6), 하루 1개 시작·종료 구간, 명시적 휴일 목록을 가집니다. 야간을 넘는 구간·점심시간·복수 근무 구간은 후속입니다. 공휴일 자동 수집은 없으며 관리자가 입력합니다.
- 실제 시각은 UTC로 저장하고 화면은 한국시간(KST)으로 표시합니다. 계산은 달력의 시간대에서 수행합니다.
- 서머타임으로 중복되는 경계 시각은 첫 발생을 사용합니다. 존재하지 않는 경계는 최초 유효 분으로 전진합니다(최대 180분). 구간의 실제 UTC 경과 시간을 사용합니다.
- 목표는 1~10080 업무분이며 응답 목표는 해결 목표 이하입니다. 요일·휴일은 중복 불가입니다. 계산 한도는 3660일이며 이 안에 목표를 배정할 수 없는 정책은 거부합니다.
- 누적 시간은 정수 마이크로초로 계산하여 잦은 평가에서 소수 초가 유실되지 않습니다.

## 상태 전이와 시계

| 사건 | 응답 시계 | 해결 시계 |
|---|---|---|
| 접수 | 시작 | 시작 |
| 담당자 배정 | 계속 진행 | 계속 진행 |
| 첫 START | 응답 완료 | 계속 진행 |
| WAIT | 이미 응답 완료 | pause_on_pending=true이면 정지, false면 진행 |
| RESUME | 응답 완료 유지 | 남은 예산을 재투영한 기한으로 재개 |
| RESOLVE | 응답 완료 유지 | 해결 완료 |
| REOPEN | 응답 완료 유지 | 기존 누적 시간을 이어서 진행, 해결 상태였던 구간 제외 |
| CLOSE | 완료 유지 | 완료 유지 |

첫 응답은 이 버전에서 **처리 시작(START)** 으로 정의합니다. 배정·댓글은 응답 완료로 간주하지 않습니다. 목표 기한에 정확히 완료하면 준수이고 그 이후는 초과입니다. 업무 종료 시각이 기한인 상태로 다음 날까지 미처리이면 비업무시간이라도 기한 초과입니다. 이미 초과한 상태에서 대기·재개방해도 초과를 초기화하지 않습니다.

SLAClockEvent는 전이 시각과 누적 시간·기한을 기록합니다. 정책·달력·시계 이벤트·알림 이벤트는 DB에서 append-only입니다. 조직 간 참조도 DB 트리거로 거부합니다.

## 임박·초과 알림

정책의 warning_percent(1~99)에 도달하면 임박, 기한을 넘으면 초과 알림을 생성합니다. SLAAlert는 (시계, 응답/해결, 임박/초과)마다 1개이며 Notification은 (수신자, 알림 이벤트)마다 1개입니다. 재시도·복수 평가자·재개방으로 같은 수준의 알림을 재발송하지 않습니다. 평가가 늦어 이미 초과했다면 과거 임박 알림을 추가 생성하지 않습니다.

수신자는 평가 시점의 활성 담당자와 해당 조직의 활성 서비스 관리자 중 해당 티켓 처리 권한이 있는 사람입니다. 해당자가 없으면 SLAAlert 기록은 남고 개인 알림은 생성되지 않습니다. /notifications와 API는 현재 본인 수신분 중 여전히 티켓 접근이 가능한 건만 제공합니다. 다른 수신자 알림의 조회·읽음 표시는 불가능합니다. 과거 알림을 새 담당자에게 소급 전달하지는 않습니다.

**현재 알림 채널은 애플리케이션 알림함입니다. 이메일·메신저 발송은 없습니다.** Outbox에는 이벤트를 남기지만 기존 처리기는 로컬 sink입니다.

## API 추가

기존 세션·CSRF·멱등키 규약을 따릅니다. 아래 생성/명령에는 Idempotency-Key가 필수입니다.

| 메서드·경로 | 사용자 | 입력·응답 |
|---|---|---|
| GET/POST /api/v1/sla/calendars | 서비스 관리자 | POST: name,timezone,weekdays[],starts_at,ends_at,holidays[] / 201 달력 |
| GET/POST /api/v1/sla/policies | 서비스 관리자 | POST: name,calendar_id,priority(1..5),response_minutes,resolution_minutes,warning_percent,pause_on_pending / 201 정책·버전 |
| GET /api/v1/notifications | 본인 | 기존 limit·cursor 페이지 규약 / 알림 목록 |
| POST /api/v1/notifications/{id}/read | 본인·현재 접근 가능 | 빈 JSON 객체 / 200 id,read_at. 반복 호출 시 최초 읽음 시각 유지 |

정책·달력은 게시 후 불변이므로 expected_version 갱신 API는 없습니다. 정책 버전은 서버에서 직렬 생성합니다. 목록에는 모든 게시 이력이 포함되며 새 티켓에는 우선순위별 최고 버전을 적용합니다.

티켓 목록·상세 응답에 sla(null 또는 객체)를 추가했습니다. policy_id,policy_name,policy_version,timezone와 response/resolution의 state,target_minutes,elapsed_seconds,remaining_seconds,percent,due_at,completed_at,paused를 포함합니다. paused이면 해당 due_at은 null입니다. state는 RUNNING/AT_RISK/PAUSED/MET/OVERDUE이며 이전에 초과했다면 정지 중에도 OVERDUE일 수 있습니다. 일반 조회는 시계나 알림을 쓰지 않습니다.

## 평가 작업 운영

```bash
DEBUG=1 python manage.py evaluate_sla
```

한 번에 평가 예정 시각이 지난 최대 500개를 처리합니다. 운영에서는 환경의 스케줄러로 **매분 반복 실행**해야 합니다. 개발 서버 시작만으로 주기 실행되지는 않습니다. next_evaluation_at 부분 인덱스로 후보를 고르고 조직→시계 순서의 잠금으로 업무 명령과 평가를 직렬화합니다. 알림 생성·시계 갱신·outbox는 같은 트랜잭션이며 외부 네트워크 호출을 하지 않습니다.

500개를 초과하는 처리량·정밀한 지연 목표는 후속 용량 검증 대상입니다. 실행 주기에 따라 알림이 늦어질 수 있지만 화면의 기한·초과 판단은 현재 시각으로 계산합니다.

## 검증

주말·휴일, 경계 시각, 서머타임 전환, 소수 초 보존, 정책 버전 고정, 대기 옵션, 재개방, 기한 초과 보존, 알림 중복·수신 권한·회수, 원자적 롤백, DB 보호를 자동 검증합니다. PostgreSQL에서는 중복 평가자와 동시 정책 게시를 실제 별도 연결로 확인합니다.

브라우저에서는 달력·정책 게시→새 장애 적용→배정→처리 시작·대기·재개·해결·종료, 알림함의 초과 표시·읽음 처리와 모바일 레이아웃을 확인했습니다. 브라우저 알림 검증에는 합성 과거 티켓을 사용했습니다.

다중 SLA·고객 계약별 우선 선택·연락 목표·정책 비활성화·소급 이관·여러 경고 단계·관리자 단계별 에스컬레이션·외부 알림은 후속 범위입니다.
