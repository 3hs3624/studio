# 계정·세션 통제 — 1차 구현

기준일: 2026-11-06. 로컬 인증 기반의 계정/세션 통제 보강입니다. 실제 SSO·계정 생성/인사 연계·권한 신청 다단계 승인·Change 실행 권한분리의 완료를 뜻하지 않습니다.

## 제공 기능

조직 관리자는 /admin/access에서 계정을 중지·재활성화하거나 모든 기존 세션을 회수할 수 있습니다. 이유와 사용자 expected_version이 필수이며 기존 멱등키·조직 잠금·감사/outbox 원자성을 사용합니다. 자신의 계정 중지, 마지막 활성 관리자 중지, 열린 처리 배정 및 대기 중 서비스/구매 승인이 있는 계정의 중지는 거부합니다. 먼저 재배정하거나 승인 대기 건을 취소/정리해야 합니다. 재활성화가 Django User의 별도 is_active=false를 해제하지는 않습니다.

역할 변경과 그룹 소속 변경은 대상의 세션 epoch를 회전합니다. 권한/조직/활성 상태와 함께 로그인 시 바인딩한 값을 다음 보호 요청에서 검사합니다. 회수 뒤 재활성화·역할 복구를 해도 이전 세션은 복구되지 않습니다. 기존 연결을 강제로 종료하는 푸시 방식이 아니라 다음 HTTP 요청 시 차단합니다. 실행 중 읽기 요청을 소급 취소하지 않습니다. 쓰기 명령은 조직 잠금 획득 후 세션 바인딩을 재검사합니다.

회수된 API 세션은 첫 요청에서 SESSION_REVOKED/403 및 로그아웃, 이후 미인증은 401입니다. HTML은 로그인 화면으로 이동합니다. 회수는 신규 로그인을 금지하는 기능이 아니며 계정을 중지해야 신규 업무 접근을 차단할 수 있습니다. 배포 이전의 바인딩 없는 로그인도 다시 인증해야 합니다.

## API

- POST /api/v1/admin/persons/{id}/account: active(boolean),reason,expected_version
- POST /api/v1/admin/persons/{id}/revoke-sessions: reason,expected_version
- GET /api/v1/admin/security-events: limit,cursor. 조직 관리자만 현재 조직 이력 조회

모든 명령은 세션 인증·CSRF·Idempotency-Key가 필요합니다. 관리자 권한은 해당 조직만 허용합니다. epoch 값/세션 키/비밀번호/쿠키/토큰은 API와 감사에 내보내지 않습니다.

## 접속 기록

SecurityEvent에 LOGIN_SUCCESS/LOGIN_FAILED/LOGOUT/SESSION_REVOKED, 시각·조직/식별 가능한 사용자·추적 ID를 기록합니다. 제출한 사용자명/비밀번호·본문·IP를 저장하지 않습니다. 로그인 실패와 매핑 불가 사용자는 조직을 추정하지 않으므로 organization/person은 null이며 조직 관리자 화면에 표시하지 않습니다. 전체 실패 기록을 조회하는 전역 보안 운영 화면·SIEM 전달·로그 보존/파기 정책은 후속입니다.

이 기록은 SQLite/PostgreSQL에서 append-only 및 조직 경계 트리거로 보호합니다. 관리자 화면은 현재 조직 최근 50건, API는 기존 페이지 규약을 사용합니다. 접속 이력은 모든 데이터 조회/다운로드에 대한 감사 로그와 다릅니다. DB 관리자까지 포함한 절대 불변을 보장하지 않습니다.

## 운영·제약

role/group 변경·중지/재활성화/회수는 제공 API를 사용해야 epoch가 회전하며 회수 근거가 남습니다. 임의 SQL로 삭제/재부여하거나 is_active를 변경한 후 되돌리는 행위를 이 API의 회수 보장으로 해석하지 않습니다. 외부 IdP/인사 이벤트는 향후 같은 회수 계약을 호출해야 합니다. 주기 계정 만료·대결/승인자 자동교체·신규 권한 부여의 독립 승인·공유 로그인 제한은 후속입니다. 기존 요청/구매 자기승인 차단과 기존 역할 보호를 유지하며 미래 Change/배포의 요청/승인/실행 분리는 별도 개발해야 합니다.

0008 마이그레이션에 Person.session_epoch와 SecurityEvent를 추가하고 기존 조직·불변 트리거를 제거/재설치합니다. 운영 DB 역방향 변경은 복원 계획 없이 수행하지 않습니다. 검증은 테스트/폐기 가능한 DB에서만 수행합니다.
