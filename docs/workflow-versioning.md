# Workflow 버전 관리 — 확정 개발 범위 초안

기준일: 2026-11-06. 사용자가 추가한 3단계 개발 범위입니다. 현재 카탈로그 버전/단일 승인 구현과 구분하며 아래 범용 Workflow 기능은 아직 구현하지 않았습니다.

## 필수 데이터와 수명주기

- WorkflowDefinition: 조직 내 코드·이름·업무 소유자·신규 시작 허용 여부·현재 게시 버전 참조
- WorkflowVersion: 정의 ID·단조 증가 버전·DRAFT/PUBLISHED/RETIRED·폼/상태/조건/승인/타이머/권한 스냅샷·편집 row_version·체크섬·작성/검토/게시 주체와 시각·변경 사유
- WorkflowVersionEvent: 작성/수정/검토/게시/중단/복제 이력과 비교 근거. 승인·게시 후 정의 본문은 DB에서 불변
- WorkflowInstance: 업무/요청 ID와 실행 버전을 고정. 노드 실행·할당·승인·타이머는 해당 버전 참조

초안은 권한 있는 편집자가 row_version 검사 후 수정합니다. 편집 충돌·잘못된 그래프/분기/역할·누락된 종료/도달 불가 상태·허용되지 않은 표현식은 게시 전 거부합니다. 게시와 신규 시작 버전 선택은 원자 처리하며 동시에 게시해도 버전/활성 포인터가 충돌하지 않도록 합니다. 임의 사용자 Python/JS/SQL 실행은 허용하지 않습니다.

## 게시·중단·복구

검토자는 해당 버전 작성자와 독립하도록 정책을 적용합니다. 게시된 버전은 덮어쓰지 않고 새 초안을 복제하여 개정합니다. 신규 요청은 게시된 현재 버전을 고정하고 접수 화면 이후 버전이 바뀌면 서버가 충돌을 알려 새 버전 확인을 요구합니다. 사용자가 보지 않은 승인 규칙으로 조용히 접수하지 않습니다.

기존 진행 건은 새 버전 게시/기존 버전 중단 이후에도 고정한 버전으로 진행합니다. RETIRED는 신규 시작 금지이며 실행 중인 요청을 취소하지 않습니다. 정의 전체 신규 시작 중단과 특정 버전 퇴역을 구분합니다. 과거 정의로 복구할 때도 이전 버전을 수정/활성화하지 않고 새 버전으로 복제·검토·게시합니다. 실행 중 인스턴스의 강제 버전 이관은 1차 범위에서 제공하지 않습니다.

## 3단계 백로그와 완료 기준

| 순서 | 개발 단위 | 완료 기준 |
|---|---|---|
| WF-01 | 정의·초안·복제·버전 목록/비교 | 조직/역할 제어·row_version·변경 주체/사유·차이 표시 |
| WF-02 | 정의 검증·독립 검토·게시 | 잘못된 정의/자기검토 거부, 게시 본문 불변, 동시 게시 일관성 |
| WF-03 | 신규 시작 버전 선택·인스턴스 고정 | V1 접수 후 V2 게시에도 기존 승인/상태/필드 규칙 유지 |
| WF-04 | 신규 시작 중단·버전 퇴역·과거 복제 복구 | 중단 버전으로 신규 접수 차단, 기존 진행 보존, 복구도 새 버전 |
| WF-05 | 다단계/조건부/병렬 승인·타이머·대결 | 승인자 변경·취소/타임아웃 경합·재시도에서 중복 결정/작업 없음 |
| WF-06 | 폼·서버 검증·권한·운영 Console | 조건부/숨김 필드도 서버 권한 적용, 지연·실패 작업 조회·통제된 재처리 |

필수 인수 시나리오: V1 진행 중 V2 게시, 오래된 접수/편집, 두 관리자 동시 게시, 게시 본문 SQL 수정 시도, 잘못된 분기/역할, 타 조직 복제/조회, 자기검토, 버전 중단 후 신규/기존 요청 차이, 과거 버전 복제 복구, 승인/취소·타이머 경합, 실행 이력·멱등 재처리, 권한 회수 후 편집/게시 차단. 화면 존재만으로 완료 처리하지 않고 PostgreSQL 실제 연결 동시성·브라우저 E2E 증적을 남깁니다.

SSO 단계에서는 로컬 로그인과 외부 인증의 사용자 연결/회수 계약을 통일합니다. Workflow의 버전 관리 모델과 카탈로그 양식 버전 연결을 설계하고 이중 정본/규칙 불일치를 피해야 합니다. 현재 서비스 요청과의 이행 방법은 실제 WF 구현 시 기존 진행 건 보존을 전제로 확정합니다.
