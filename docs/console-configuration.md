# 운영 콘솔 구성 관리

## 조직·권한 관리

`/console/access`에서 사용자, 역할·권한, 담당 그룹, 계정·세션, 변경 이력을 탭으로 구분합니다.
탭 주소는 `?tab=users|roles|groups|accounts|history`로 유지됩니다.
기존 역할 배정·담당 그룹 소속·계정 정지 및 세션 회수 동작을 재사용합니다.
권한·소속 변경 화면에서 사유를 입력하면 감사 이력에 기록합니다. 기존 API와의 호환성을 위해 해당 API의 reason은 선택 항목으로 유지합니다.
권한·계정 관리는 시스템 관리자 역할이 필요합니다. 개발자·운영자의 운영 콘솔 접근 권한만으로 계정 관리 권한을 부여하지 않습니다.
현재 역할은 플랫폼이 제공하는 기본 역할이며 임의 역할/권한 정의 편집은 이번 범위에 포함하지 않습니다.
미저장 편집이 있는 상태에서 탭·페이지를 이동하면 브라우저 확인을 표시합니다.

## 플러그인 목록과 상세

`/console/plugins`에서 설치 플러그인의 버전, 사용 여부, 설정 버전, 호환 상태와 최근 성공 실행을 확인합니다.
상세는 `/console/plugins/{plugin_id}?tab=overview|settings|test|runs|changes`입니다.
설정 화면은 manifest의 settings_fields 정의를 읽어 boolean/string/integer/enum 입력을 생성합니다.
설정 저장에는 최신 설정 버전, 실제 설치 manifest digest, 변경 사유가 필요합니다.
배포로 코드/계약 해시가 바뀌면 기존 설정은 보존하되 설정 탭에서 확인·재저장해야 실행됩니다.
미리보기 입력·출력 텍스트 본문은 실행/실패/감사 이력에 기록하지 않습니다. 성공 이력은 길이·버전·실행자, 실패는 오류 코드와 설정 버전만 기록합니다.
번호 발급 이력에는 실제 발급된 업무번호도 저장합니다. 실패 재시도 이력은 같은 요청 키의 중복 기록을 방지합니다.
실행·실패 이력과 설정 변경 이력은 현재 조직 기준 최근 50건입니다.

### 추가된 업무번호 생성 플러그인

식별자: `number.generate`, 버전: 1.0.0.

1. 플러그인 목록에서 업무번호 생성을 선택합니다.
2. 설정 탭에서 접두어, 날짜 형식, 구분자, 순번 자릿수, 초기화 주기를 지정합니다.
3. 사용을 선택하고 사유를 입력한 후 설정을 저장합니다.
4. 실행 테스트 탭에서 예상 번호 확인 또는 실제 발급을 선택합니다.
5. 실제 발급 후 새 번호가 필요하면 '새 발급 준비'를 누릅니다.
6. 실행 이력에서 발급 번호·실행자·실패 코드를 확인합니다.

기본값: SR / YYYYMM / - / 5자리 / 월별. 예: SR-202611-00001.
서버 날짜(Asia/Seoul)를 사용하며 실제 발급 요청이 임의 날짜나 순번을 지정할 수 없습니다.
미리보기는 순번을 소비하지 않습니다. 실제 발급은 조직 잠금과 DB 유일성 제약을 적용하며 같은 요청 키의 재전송에는 같은 번호를 반환합니다.
날짜 없는 형식의 월별 초기화처럼 번호 중복을 유발하는 설정은 거부합니다. 기간 자릿수를 소진하면 오류를 표시하고 순번은 증가하지 않습니다.
설정 조합을 바꾸면 별도 번호 체계로 순번을 관리합니다. 과거 발급 번호와의 중복은 형식 변경 후에도 DB에서 차단합니다.
자동 엔티티 업무번호 입력이나 워크플로우 자동 호출은 후속 연결 범위입니다. 이번 범위에서는 콘솔에서 미리보기·실제 발급까지 지원합니다.
새 플러그인 코드는 개발자가 번들 레지스트리에 추가하고 검증·배포합니다. 운영자가 임의 실행 코드를 업로드하는 기능은 제공하지 않습니다.

API:
- POST `/api/v1/admin/plugins/number.generate/configuration`
- POST `/api/v1/admin/plugins/number.generate/preview`
- POST `/api/v1/admin/plugins/number.generate/issue`

실행 요청은 `expected_version`, `manifest_digest`, `input: {}`와 Idempotency-Key가 필요합니다.
설정은 `enabled`, `configuration`, `expected_version`, `manifest_digest`, `reason`을 사용합니다.

## 공통코드 관리

시스템 관리 > 공통코드 관리(`/console/codes`)에서 코드 그룹을 만들고 선택하여 코드 그리드를 편집합니다.
현재 조직의 여러 업무·엔티티에서 공유하는 코드입니다. 조직을 넘는 전역 코드 편집은 제공하지 않습니다.
코드와 그룹 식별자는 생성 후 유지하고, 표시 이름·설명·정렬 순서·사용 여부를 변경할 수 있습니다.
코드는 삭제하지 않고 사용 중지합니다. 생략한 기존 코드는 삭제되지 않습니다. 시스템 필수(locked) 그룹은 조회만 가능합니다.
그룹 설정 버전으로 동시 편집 충돌을 막고, 저장은 트랜잭션으로 처리합니다. 한 번에 최대 100개 코드를 저장합니다.

엔티티의 선택형 필드에서 '공통코드 그룹'을 선택하면 직접 입력한 선택지 대신 그룹의 사용 중인 코드를 불러옵니다.
업무 데이터에는 표시 이름이 아닌 안정적인 코드값을 저장합니다. 중지된 코드/그룹은 신규 입력에서 거부하고 기존 데이터는 유지합니다.
기존 데이터 표시에는 현재 코드 이름을 사용합니다. 과거 특정 시점의 표시 이름을 별도로 스냅샷으로 저장하는 기능은 포함하지 않습니다.
그룹 상세에서 초안·게시 정의를 포함한 사용 엔티티와 변경자·변경 사유를 확인합니다.
기존 고정 업무 상태 전체를 공통코드로 자동 치환하지 않으며, 새로 연결한 엔티티 선택형 필드부터 적용합니다.

API:
- GET/POST `/api/v1/admin/code-groups`
- GET/POST `/api/v1/admin/code-groups/{id}`
- POST `/api/v1/admin/code-groups/{id}/items`

## 권한과 업데이트

플러그인·공통코드 관리에는 개발자·운영자·시스템 관리자 중 하나의 역할이 필요합니다.
화면과 API 모두 현재 조직 및 권한을 확인합니다.

기존 Render/Neon 배포와 로컬 Docker는 같은 소스·0013 마이그레이션을 사용합니다.
로컬 PC에서는 기존 설정/계정/볼륨을 보존하고 [업데이트 절차](entity-relationships.md#로컬-docker-업데이트)에 따라 소스를 덮어쓴 뒤 다음을 실행합니다.

```powershell
python deploy/local_split/control.py up
python deploy/local_split/control.py verify
```

새 플러그인은 설정 탭에서 사용 여부를 저장한 후 실행하십시오. 계정 비밀번호는 변경하지 않습니다.
