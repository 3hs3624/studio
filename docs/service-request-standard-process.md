# 서비스요청 표준 프로세스

서비스 카탈로그의 **서비스 요청**에서 신청하면 게시된 워크플로우가 실행됩니다.

1. **서비스 요청 등록** — user1이 요청 제목과 내용을 입력합니다.
2. **요청부서 결재자 승인** — 같은 요청부서의 user_auth1이 승인 또는 반려합니다. 서비스 승인함에서도 대기 건을 확인할 수 있습니다.
3. **접수 및 담당자 배정** — 서비스요청 접수그룹(worker1, worker2, worker3) 중 한 명이 접수하고 세 명 중 조치 담당자를 선택합니다.
4. **조치** — 선택된 담당자에게만 처리 권한을 부여합니다. 조치 내용을 입력해야 진행합니다.
5. **사용자 확인** — 신청자에게 돌아갑니다. 정상 확인이면 종료, 아니오이면 기존 담당자의 조치로 되돌아갑니다.
6. **종료** — 연결된 서비스요청을 CLOSED로 종료하고 완료 시각을 적기처리율 산정에 반영합니다.

## 구성 위치

기존 시스템 관리자 계정으로 운영 콘솔에서 확인합니다.
- 화면 관리: 서비스요청 공통 화면(SR_STANDARD_SCREEN)
- 결재선 관리: 요청부서 결재선(SR_STANDARD_APPROVAL)
- 워크플로우 관리: 서비스요청 표준 프로세스(SR_STANDARD)
- 업무 메뉴 연결: service-request
- 서비스 카탈로그: 서비스 요청(SR_STANDARD_REQUEST)
- 사용자/부서/그룹 관리: 요청부서, 서비스 운영부서, 서비스요청 접수그룹

운영자1~3은 서비스 처리 담당자(AGENT)입니다. 플랫폼·보안·개인정보 관리 권한은 자동 부여하지 않습니다. 다섯 새 계정은 초기 비밀번호로 로그인한 뒤 비밀번호를 변경해야 합니다. 기존 계정은 변경하지 않습니다.

초기 버전은 사용자 요청에 따른 배포 프리셋으로 자동 검증하여 구성합니다. 버전 사유에 수동 독립 검토가 아님을 명시합니다. 이후 콘솔에서 변경하면 기존 초안·독립 검토·게시 절차를 사용합니다. 기존 진행 건은 자신이 참조한 게시 버전을 유지합니다.

## 실행 계약

워크플로우는 person 유형 필드와 그룹 선택 범위, FIELD_USER(선택 담당자), STARTER(신청자) 할당을 사용합니다. 숨김/읽기/입력 규칙과 필수 검증을 서버에서 적용합니다. catalog_only는 카탈로그를 거치지 않은 신규 실행을 차단합니다. close_on_complete와 ticket_assignee_field로 실제 요청의 종료 상태와 담당자를 반영합니다.

`python manage.py setup_service_request --organization-id <조직 UUID> --password-file <개인 비밀번호 JSON>`로 새 환경에 설치할 수 있습니다. 비밀번호 JSON은 다섯 사용자 ID를 키로 갖는 객체이며 소스에 저장하지 않습니다. Render에서는 기존 서비스 설정에 두 키(STUDIO_SR_PROVISION_ORGANIZATION_ID, STUDIO_SR_PASSWORDS_JSON)를 병합합니다. 최초 구성 후 마커를 검사해 재배포 시 계정·비밀번호·운영자가 수정한 구성을 덮어쓰지 않습니다. 같은 ID나 메뉴 연결이 이미 있으면 임의 대체하지 않습니다.

초기 설치 시 실제 엔진으로 전체 경로와 재조치 경로를 롤백 트랜잭션 안에서 검증합니다. 검증 요청은 운영 데이터로 남지 않습니다. 비밀번호와 비밀 값은 로그에 출력하지 않습니다.
